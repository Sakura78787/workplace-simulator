# 架构与业务决策日志 (Decision Log)

本文件用于记录项目推进过程中的关键业务砍档、技术妥协及架构决策，解释“为什么我们选择这样做”。

## 2026-04-20 进度冲刺与 MVP 边界定调

在完成 Task 11 后，产品与执行方针对 `roadmap_to_100_percent.md` 的疑点进行了最终决策，确立了**“极简落地、控制成本、快速验证”**的原则。以下为关键决定：

1. **废弃 iOS 专项适配 (Task 15)**
   - **决定内容**：本期 MVP 明确不解决 iOS Safari / 微信环境下的 `html2canvas` 导出异常、橡皮筋回弹和键盘遮挡问题。全量保 Android 及 X5 内核。
   - **Why**：iOS 的前端渲染坑点极多，修补性价比极低。不让技术债卡住产品整体验收。

2. **砍掉账户与登录系统，采用匿名同步 (Task 13/14)**
   - **决定内容**：不接入微信静默授权，不用手机验证码。
   - **Why**：降低用户的进入门槛，提高裂变转化率。
   - **How to apply**：使用本地生成的 UUID 追踪。A/B 测试仅记录转化点击（建表 `ab_clicks`）；图鉴上报采用纯静默元数据同步（建表 `pokedex_sync`）。榜单只需展示脱敏后的匿名玩家代号。

3. **零新增环境的新职业拓展 (Task 16)**
   - **决定内容**：未来新增研发(RD)与测试(QA)等岗位时，绝对不改底层机制，不新增任何独立或特殊关卡环境。
   - **Why**：降低代码变动风险与心智成本。所有职业均能套入这套底层情绪框架。
   - **How to apply**：强制沿用“热身->甩锅->插单->死线->背锅”这 5 大主线流程，只在 `game-data.json` 里做纯文本换皮。

4. **极简裂变，不搞空降逻辑 (Task 17)**
   - **决定内容**：扫别人分享的海报二维码后，新用户统一直达项目首页。
   - **Why**：复原他人的“死亡现场”涉及复杂状态透传与恢复，且极有可能暴露合规边界或卡死流程。
   - **How to apply**：不做复杂的 deep link 参数解析，直接拉新。
